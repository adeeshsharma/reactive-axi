# fixtures

Throwaway real apps used to validate `reactive-axi` against actual dev servers — not published, not part of the `reactive-axi` package.

Naming convention: `{framework}[-{reactMajorVersion}]` for React fixtures (`vite-react-18`), `{framework}-{majorVersion}` for the others (`svelte-4`) — the version suffix is omitted only for "whatever's current," so every fixture's name states exactly what it's proving.

Members:

- `vite-react-19/` — plain, unmodified `npm create vite@latest -- --template react` output (has accumulated some real dogfooded content since, intentionally, not test debris). The load-bearing Phase 1 fixture. Also carries a permanent `#vendor-components` section (`@radix-ui/react-accordion` + `@radix-ui/react-dialog`) for the vendor-source-resolution fix — real, complex compound components (not a single button), used to prove click-to-source resolves to app code, not `node_modules`, on the React 19 `_debugStack` path.
- `vite-react-18/` — pinned React 18.3, the debugSource-era upper bookend. Same `#vendor-components` Radix Accordion/Dialog section as `vite-react-19/`, proving the fix on the `_debugSource` path.
- `vite-react-16/` — pinned React 16.14, the hard architectural floor (pre-Fiber React <16 has no fiber tree to walk at all). Needs the classic JSX runtime and legacy `ReactDOM.render` (no `createRoot`, that's an 18+ API) — see the fixture's own `vite.config.js`/`src/main.jsx` comments. Also carries the same `#vendor-components` Radix Accordion/Dialog section (confirmed real: Radix's peer deps allow React 16.8+, verified booting cleanly with zero console errors).
- `tanstack-start/` — bootstrapped via `npx @tanstack/cli create --blank -y`, latest (React 19.2, Vite 8). Its `package.json` has a real `vite` devDependency, which matters for framework *detection* order - don't let it get misclassified as plain Vite. Also carries a `#vendor-components` section in `src/routes/index.tsx`.
- `tanstack-start-react-18/` — same, with `react`/`react-dom` overridden to `^18` - confirmed no peer conflicts. Same `#vendor-components` section.
- `nextjs-pages-router/`, `nextjs-app-router/` — bootstrapped via `create-next-app@latest`, latest (Next 16.3.0, React 19.2.8). `nextjs-pages-router/` carries the same `#vendor-components` Radix Accordion/Dialog section, added specifically because Next's webpack-style transformed chunk URLs don't expose `node_modules` pre-sourcemap-resolution the way Vite's do — proves the vendor-source-resolution fix's server-side authoritative check, not just the Vite-URL client-side shortcut. `nextjs-app-router/`'s default scaffold has **no client component at all** - every element in it is a Server Component with zero client-side Fiber presence, meaning nothing was clickable at all before this was noticed. Added a real `"use client"` island, `app/VendorComponents.js` (imported and rendered from the still-server `page.js`), carrying the same vendor Accordion/Dialog - without it, App Router had no live way to test click-to-source at all, vendor or not. Confirmed live: resolves to the exact real line in `VendorComponents.js`.
- `nextjs-pages-router-react-18/`, `nextjs-app-router-react-18/` — same Next major, `react`/`react-dom` overridden to `^18` (confirmed valid - App Router only requires 18+, not specifically 19). Both carry the same `#vendor-components`/`VendorComponents.js` additions as their default-version siblings. Real finding: even at a genuinely-confirmed React 18.3.1 install, `nextjs-app-router-react-18` still resolves click-to-source via the `_debugStack` path, not `_debugSource` - Turbopack/Next's own SWC-based compiler doesn't guarantee the same React-version-keyed dual-path split Vite's `@vitejs/plugin-react` does. Resolution is still correct either way (`findDebugInfoKind` handles both paths gracefully), just worth knowing this isn't a strict "React ≤18 always means debugSource" guarantee across every framework.
- `cra-app/` — Create React App (`react-scripts` 5.0.1, officially deprecated Feb 2025). Scaffolded successfully at React 19.2.8 despite reports that the scaffolder fails against 19. **Must run with `DISABLE_ESLINT_PLUGIN=true`** - react-scripts' bundled `eslint-webpack-plugin` otherwise resolves the much newer ESLint hoisted from `packages/reactive-axi`'s own devDependency inside this pnpm workspace and fails to compile - a real pnpm-workspace toolchain collision, not a React-version issue. The eventual CRA adapter must set this env var. Also carries the same `#vendor-components` section in `src/App.js`.
- `vue-3/` — plain, unmodified `npm create vite@latest -- --template vue` output (Vue 3.5.41). Vue 2 is explicitly out of scope (EOL since Dec 2023, needs an entirely different plugin/compiler) - see `memory-bank/vue-svelte-plan.md`. Also carries a `#vendor-components` section with **two** distinct vendor cases, deliberately different from each other: `reka-ui` (a real published headless-UI library) resolves to `App.vue` — confirmed live, it does **not** reproduce the vendor-source bug, because its package entry point is precompiled output, never the raw `.vue` SFC source it also happens to ship; and `@fixture/vue-vendor-ui-kit` (see below), which does.
- `vue-vendor-ui-kit/` — a small, real, un-precompiled compound-component library (raw `.vue` SFC source, no build step: Accordion + Dialog, multiple sub-components each) — not a testable app itself, a dependency `vue-3/` consumes via `workspace:*`. Stands in for a monorepo-local design-system package, which pnpm links as a symlink. This is the fixture's actual reproduction of the vendor-source bug for Vue (confirmed live: clicking its rendered trigger resolves to its own file, not `vue-3/`'s usage site) and, once the fix lands, the live proof that a symlinked local package correctly classifies as app code, not vendor. `vue`/`@vue/*` are declared as `peerDependencies`, not `dependencies` — declaring `vue` as its own dependency caused a real, confirmed duplicate-module/broken-reactivity bug (an injected `ref` arrived as a plain unwrapped value in a consuming component) even though pnpm resolved both to the same physical install; peer-dependency is the correct, standard shape for a library meant to always run inside a host app's own Vue instance.
- `svelte-4/` — pinned Svelte 4.2.20, with the whole toolchain pinned together (`@sveltejs/vite-plugin-svelte@^3.1.2` + `vite@^5`, since that plugin dropped Svelte 4 support starting at its own v4 release). `Counter.svelte`/`main.js` were hand-converted away from the scaffolder's default Svelte-5/runes output to real legacy syntax (`let` instead of `$state`, `on:click` instead of `onclick`, `new App({target})` instead of `mount()`) - don't "fix" this back to match `svelte-5/`, that would break the Svelte-4 pin entirely. Also carries a `#vendor-components` section using `bits-ui@0.21.16` (the last pre-Svelte-5 release, confirmed via real peer-dep and file-listing checks to target Svelte 4 and ship raw `.svelte` source) - same Accordion/Dialog archetypes as `svelte-5/`, same library family, real parity across both versions.
- `svelte-5/` — plain, unmodified `npm create vite@latest -- --template svelte` output (Svelte 5.56.8, runes). The two Svelte fixtures exist specifically because Svelte 4's and 5's compilers report `__svelte_meta.loc` line/column with different indexing (0-indexed vs 1-indexed, confirmed by a real spike, not assumed) - see `memory-bank/vue-svelte-plan.md`. Also carries a `#vendor-components` section using `bits-ui@^2.18.1` (Accordion + Dialog) - confirmed live to reproduce the vendor-source bug (resolves into `node_modules/bits-ui/dist/...`), and to demonstrate the framework's honest-fallback limitation when no app-authored DOM ancestor wraps the vendor component at all.

Each fixture is its own `"private": true` workspace package with its own dependency tree.

## Vendor UI components (vendor-source-resolution fix)

Every framework fixture above that has one carries a permanent `#vendor-components` section: real npm dependencies (headless-UI component libraries), not application code, used to verify click-to-source resolves to the app's own usage site rather than into the library's internals. These are load-bearing test infrastructure, not spike debris - keep them when touching these fixtures for unrelated reasons. Full empirical findings (which libraries do/don't reproduce the bug and why, the Vite-already-resolves-symlinks discovery, the Svelte coverage limitation) are in `memory-bank/techContext.md`.
